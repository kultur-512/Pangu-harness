# 交接流程:状态机与路由

> 三 agent 协作的图定义(L14 图工程:节点、边、共享状态、路由规则)。
> 目标:让开发变成**可审计、可局部修复**的图,而不是藏在单个 agent 上下文里的环。
> 框架来源:learn-harness-engineering L13(loop)/ L14(graph) + multi-agent-pattern(Coordinator)。

## 一、节点(谁做什么)

| 节点 | 类型 | 产出 | 拥有者 |
|------|------|------|--------|
| **Implement**(编码) | agent(全工具) | 代码 + 测试 + 提交 + 证据 | 编码 agent |
| **Review-1**(一级验收) | agent(只读) | 验收结论 / 返工指令 | 一级审查 |
| **Review-2**(二级复审) | agent(只读) | 审查报告 / 新发现 / 缺口条目 | 二级审查 |
| **Archive**(归档) | 确定性操作 | 交接归档 + feature 状态更新 | 任一 agent 按流程执行 |

## 二、边与路由规则

```
              ┌──────────────────────────────┐
              ▼                              │
[Implement] ──提交批次──▶ [Review-1] ──通过──▶ [Review-2] ──通过──▶ [Archive]
    ▲                        │ 返工             │ 新发现
    │                        ▼                  ▼
    └────────── 返工指令(带证据) ──┐      [Implement 或 Review-1]
                                  │            (按缺陷类型路由)
                                  └────────────┘
```

| 边 | 条件 | 目标 | 说明 |
|----|------|------|------|
| submit | DoD 五连门禁绿 + 已提交 | Review-1 | 编码交出:证据 + 代码 + 交接 |
| pass-1 | 逐项核对通过 + 全量绿 | Review-2 | 一级验收结论写入 docs |
| rework-1 | 任一核对项未落实/回归 | Implement | 返工指令必须带 file:line + 验证要求 |
| pass-2 | 三层复审无高危/回归 | Archive | 归档交接 + feature_list 状态更新 |
| rework-2 | 二级发现回归/高危 | Implement | 同 rework-1,注明优先级(P0/P1) |
| gap | 二级发现指令清单遗漏 | Implement(补丁) | 记录为结构性缺口 T-xx,决定是否追加补丁 |

## 三、失败回路与恢复

- **测试红**:Review-1 直接返工(不进入 Review-2)——快失败,省一轮
- **二级发现回归**:回 Implement,但**必须经 Review-1 复验**才能再进 Review-2(防止修坏)
- **信息不足**:Review-1 或 Review-2 在交接中注明"需要上下文",由编码 agent 补证据后重交
- **争议**:审查者与编码对"是否该修"分歧 → 写进 session-handoff,由人类拍板,不私下压过对方

## 四、图工程三失败规避(照搬 Zorge AgentTree 设计原则)

| 失败模式 | 本流程的规避 |
|---------|-------------|
| **Goodhart**(指标当目标) | "通过"只由门禁输出判定,不以审查者主观满意度、不以步数/字数判定;证据必须真实可见 |
| **盲视**(只看自己) | 审查者是独立上下文(不继承编码的会话);Review-1 验收指令、Review-2 复审 Review-1——检查者之间也互相检查 |
| **冲突**(多头写同一目标) | 共享工作区单一真相(`feature_list.json` 一次一个 active);审查者只读,唯一写方是编码 agent + 状态文件 |

## 五、交接工作区作为共享状态

所有节点读写同一 `.agents/` 工作区(L14:节点不互相喊话,都读写同一状态):

- **feature_list.json**:当前 feature、状态、证据、下一步——路由决定"做什么"的依据
- **progress.md**:完成/进行中/阻塞——路由决定"做到哪了"的依据
- **session-handoff.md**:当前交接(谁→谁、内容、下一步)——路由决定"下一步谁接手"的依据
- **handoff/**:历史归档(append-only)——审计与回滚依据

## 六、路由决策表(任一 agent 收尾时查)

| 我现在的状态 | 下一步 |
|-------------|--------|
| 编码完成,门禁绿,已提交 | 更新交接 → 交给 Review-1 |
| 编码收到返工指令 | 修复 → 补测试 → 门禁 → 重交 Review-1 |
| 一级验收通过 | 更新交接 → 交给 Review-2 |
| 一级验收发现返工 | 写返工指令 → 交接 → 回 Implement |
| 二级复审通过 | 归档 → 更新 feature_list(该 feature done 需证据)→ 交接 → 收工 |
| 二级复审发现回归 | 写审查报告 → 交接 → 回 Implement(注明需 Review-1 复验) |
| 二级复审发现清单遗漏 | 记录 T-xx → 交接 → 由人类决定是否追加补丁批次 |
